# Windows installer packaging

Use Python 3.11+ with the checkout's configured Windows toolchain. All new
scripts use the standard library and the checkout's GN, Ninja and 7-Zip tools;
they do not need a globally installed 7-Zip or scripts from `out/`.

The single entry point is `xenon_overlay/tools/package_windows.py`. It uses the
installer name/version generated by GN, rather than hardcoded product filenames.
The default build directory is `out/Release_64`.
Normal builds use the configured `autoninja.py` when it is available on PATH,
otherwise the bundled Ninja executable.

## Commands

Build the browser/setup/installer dependencies normally and verify the result:

```powershell
python xenon_overlay/tools/package_windows.py --build-dir out/Release_64
```

Repackage already compiled, previously validated binaries after changing only
payloads or packaging rules:

```powershell
python xenon_overlay/tools/package_windows.py --build-dir out/Release_64 --repack-existing
```

This explicit mode regenerates GN files, validates the existing installer object
and library inputs, runs the generated archive action, compiles packed resources,
and relinks only the installer. It does **not** rebuild the browser or establish
that its C++ source changes are compiled. Use the normal mode after application
code, version, branding or compiler configuration changes. Unknown GN graph
layouts fail instead of dropping extra build
stages. The previous installer is backed up in the run's evidence directory and
restored if archive creation, relinking or verification fails; intermediate
archives are not a transaction and may still belong to the unsuccessful run.
Force-terminating the process may prevent cleanup; the prior installer remains
available as `previous-installer.exe` in the evidence directory.

Verify existing artifacts without GN, compilation or repackaging:

```powershell
python xenon_overlay/tools/package_windows.py --build-dir out/Release_64 --verify-only
```

Each invocation creates a new `out/Release_64/packaging-reports/<unique>/`
directory. `--output-dir <new-directory>` selects another evidence directory;
existing report directories are never overwritten. `report.json` records the
mode, commands, result, and link to `verification/report.json`. Compression and
link logs are retained for failures as well as successful runs.

## Responsibilities

| File | Responsibility |
| --- | --- |
| `resources/windows_hosted_apps.json` | Single app-to-profile mapping consumed by GN and verification |
| `windows_electron_runtime.py` | Root runtime removal policy, TH/PLE differences and PE import checks |
| `copy_runtime_tree.py` | Generate a clean development runtime copy |
| `create_xenon_installer_archive.py` | Stage selected payloads from canonical sources and create archives using Chromium's pipeline |
| `package_windows.py` | Build/repackage orchestration and evidence collection |
| `verify_windows_installer.py` | Fresh extraction, hashes, hosted policies and archive roundtrip |
| `windows_installer_resources.py` | Read/hash the installer's PE archive resource without executing it |

TH and PLE are explicitly selected through `xenon_electron_apps` in GN args.
Their original imported releases remain intact. Hosted installer staging reads
those originals directly, so runtime logs/caches in a running build output do not
enter the installer. See [runtime policy](windows_electron_runtime.md) for the
graphics libraries, native addons, identity executables and licenses retained.

## Manifest and verification scope

The archive action writes `xenon_installer_manifest.json` beside the archives.
It records every staged path, file size and SHA-256, plus each application's
cleanup profile. The verifier rejects unsafe/colliding archive paths before
extraction, compares the complete extracted tree to that manifest, checks hosted
runtime boundaries, verifies `chrome.packed.7z` decompresses to `chrome.7z`, and
hashes the installer's embedded `B7/CHROME.PACKED.7Z` resource against the packed
archive. A missing manifest requires a new package; old historical reports are
not substituted for it.

This verifies packaging and file integrity. It does not install the product,
sign it, launch applications, or claim that startup/media tests ran. Validate
TH/PLE startup and playback separately with the actual packaged browser and its
matching N-API forwarders. Historical startup reports and fixed test counts are
never copied into a new verification report.

The verifier is also independently callable:

```powershell
python xenon_overlay/tools/verify_windows_installer.py --build-dir out/Release_64 --installer out/Release_64/<generated-installer>.exe --output-dir out/package-verification
```
