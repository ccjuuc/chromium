# Xenon 远程共享：页面、浏览器窗口与桌面

入口：`chrome://xenon-remote/`。本功能采用浏览器内主动共享，会话随共享页面结束；不安装后台服务，也不依赖 Google Chrome Remote Desktop 的注册、账号或信令服务。

## 共享范围

| 模式 | 画面来源 | 控制范围 |
|---|---|---|
| 页面 | 原生选择器选中的标签页，`TYPE_WEB_CONTENTS` | 通过受限的 DevTools Input 操作该页面 |
| 浏览器窗口 | 当前 profile 的一个浏览器窗口，`TYPE_WINDOW` | Windows 原生输入，可操作地址栏、标签栏与当前页面 |
| 桌面 | 选择的显示器，`TYPE_SCREEN` | Windows 原生鼠标、键盘输入 |

浏览器窗口模式仅覆盖选中的窗口。其他浏览器窗口和独立系统对话框不保证包含在画面中；最小化窗口可能暂停采集。页面／桌面音频沿用原生选择器返回的能力和用户选择，当前窗口模式不请求音频。当前 Windows 支持三种模式的输入；其他桌面平台可以共享画面和控制普通网页，窗口／桌面控制会显示为不可用。

## 连接步骤

1. 在被控端打开 `chrome://xenon-remote/`，选择共享范围和音频选项，通过 Chromium 原生选择器确认目标。
2. 在共享页生成并复制配对信息。
3. 接收端打开 `chrome://xenon-remote/viewer.html`，或者下述独立接收端页面，粘贴配对信息并生成应答。
4. 把应答粘回共享端完成连接。视频和输入通过双方的 WebRTC 连接传输。
5. 需要操作时，由共享端本地勾选允许控制；接收端不能自行授予控制权限。需要中文或移动端文本输入时，使用接收端的文本输入区域。
6. 可以在同一会话中重新选择共享目标。切换会撤销旧目标的控制，重新选择后再由共享端允许控制。

接收端连接成功后，视频自动占满网页可视区域，并按原比例显示完整画面。右上角的“控制”菜单显示当前操作权限，展开后可断开连接、进入／退出全屏或发送文字。断开后恢复配对界面；内置 WebUI 与独立网页使用相同布局。

首版使用手动 offer/answer 配对。没有部署自动配对服务；配对信息仅属于本次会话。默认没有第三方 STUN/TURN 服务，同一局域网可直接验证；跨 NAT 网络需要在建立会话前配置实际可用的 ICE/STUN/TURN 服务。网络不通时页面显示失败，不能把已生成配对信息视为已经连接。

共享页面关闭、刷新、渲染进程退出、停止共享或会话断开时，会撤销远程控制。接收端失焦或断开时释放按键、鼠标按钮；每条输入携带来源 generation，旧来源的事件不会被应用到新目标。

## 普通浏览器与手机接收端

独立接收端仅包含四个静态文件：`viewer.html`、`viewer.js`、`session.js`、`index.css`。无需安装扩展或原生程序。

仓库提供仅服务这些资源的 Node 工具，避免把整个源码目录暴露为静态站点：

```powershell
Set-Location H:\chromium_142\src
.\third_party\node\win\node.exe xenon_overlay\tools\remote_browser\serve_viewer.mjs
```

默认接收端地址为 `http://127.0.0.1:8787/`。供局域网其他设备访问时，显式指定监听地址：

```powershell
.\third_party\node\win\node.exe xenon_overlay\tools\remote_browser\serve_viewer.mjs --bind 0.0.0.0 --port 8787
```

在其他设备访问 `http://<该电脑局域网地址>:8787/`。需要 HTTPS 时可传 `--cert certificate.pem --key key.pem`，证书需被接收设备信任。也可以导出静态文件部署到已有 HTTPS 站点：

```powershell
.\third_party\node\win\node.exe xenon_overlay\tools\remote_browser\serve_viewer.mjs --export-dir out\remote-viewer
```

导出目录必须尚不存在。工具只提供静态接收端，不存储配对信息，也不转发媒体或输入。

## 复用的已有能力

- `DesktopMediaPickerController`：原生目标选择、缩略图与采集策略。
- `DesktopStreamsRegistry`：一次性、绑定发起页面 frame/origin 的采集令牌。
- `getUserMedia` 桌面流：复用 WebContents/Viz、窗口／屏幕捕获、音频与共享通知。
- `RTCPeerConnection`、`RTCRtpSender.replaceTrack`、DataChannel：统一音视频传输、来源切换和输入消息。
- `DevToolsAgentHost`：页内输入使用固定的 Input 命令和布局尺寸查询，不开启远程调试端口，不转发任意 CDP 命令。
- `remoting::InputInjector`、`InputEventTracker`：Windows 输入、键码映射、按键和鼠标状态释放。

`//remoting/host:win_input_injector` 从原 `:common` 中抽出 Windows 输入实现；原 Host 也依赖这个目标，没有复制注入代码。独立 `//xenon_overlay/chrome/browser:remote_input` 管理目标和输入生命周期，与 WebUI、配对方式分离，后续可用于常驻 Host。

## 代码位置

- `xenon_overlay/chrome/browser/ui/webui/xenon_remote_ui_controller.{h,cc}`：WebUI、原生选择器和本地控制开关。
- `xenon_overlay/chrome/browser/remote/remote_input_router.{h,cc}`：输入校验、目标路由、generation 与按键清理。
- `xenon_overlay/resources/webui/xenon_remote/`：共享端、接收端和通用会话逻辑。
- `xenon_overlay/tools/remote_browser/`：独立接收端服务／导出工具及测试。

### 性能：低操作延迟，兼顾文字清晰

接收端按 `requestAnimationFrame` 合并连续鼠标移动，每帧只发送最新位置，减少 DataChannel 消息和原生输入路由工作量。点击、滚轮和按键会先立即发送待处理的移动，再发送自身事件，保持顺序；撤权、切源、失焦和断开会丢弃待发移动。正常前台调度下，连续移动可能多等待一帧，点击和按键无需等待。对于同一个远端流，接收端也不再重复设置 `video.srcObject`，避免不必要的媒体重新加载。

当前仍采用 WebRTC 默认的编码、码率与拥塞控制。测试中的 GPU 加速已启用，但实际协商的是 VP8 / `libvpx` 软件编码，不能据此宣称使用了硬件编码。没有通过固定降低分辨率换取流畅度。

新增性能工具复用双进程验收的进程管理、真实采集、配对和输入路径，记录实际采集尺寸、采集页可见性及动画频率、码率、编码／解码耗时、CPU、输入到目标 DOM 和输入到接收视频像素变化的延迟：

```powershell
.\third_party\node\win\node.exe xenon_overlay\tools\remote_browser\local_performance_test.mjs --browser out\Release_64\xlb153.exe --report out\remote-performance.json --seconds 10
```

报告路径须尚不存在。默认 GPU 开启、使用无界面浏览器；可加 `--headed`。默认请求 1920×1080 窗口，必须以报告中的 `capture.width/height` 为准：本机实际采集为 **2400×1280**，`screenPixelRatio=1.25`。测试把采集页切到活动标签并让接收视频可见；早期小尺寸和后台标签的测量不作为这组对照。CPU 数值以单个逻辑核心的 100% 为单位，并非整机占用率。

2026-10-29 本机顺序测量，每种静止／滚动场景持续 8 秒，每轮点击反馈有 12 个样本。对照接收端从当前安装的旧资源包提取；新版接收端使用工作区资源：

| 指标 | 旧版接收端 | 合并移动后的接收端 |
|---|---:|---:|
| 实际采集尺寸 | 2400×1280 | 2400×1280 |
| 滚动编码帧率 | 29.82 FPS | 30.07 FPS |
| 滚动码率 | 3.26 Mbps | 2.99 Mbps |
| 高频移动：产生事件 → 实际发送消息 | 3012 → 3012 | 1240 → 280 |
| 输入到目标 DOM | 1–5 ms | 2–6 ms |
| 点击到接收视频像素变化：中位数 | 110.70 ms | 211.35 ms |
| 点击到接收视频像素变化：最大值 | 1122.70 ms | 1136.00 ms |

高频移动是 3 秒内定时分批产生的测试输入，每轮实际产生数量受调度影响，因此按各自的事件数计算合并比例；新版这轮减少约 **77%** 的消息，并保持控制权限。点击测量包含采集、传输、解码和读取视频像素，以 10 ms 定时轮询识别颜色变化，不等同于物理显示器的呈现延迟。顺序运行的样本和 CPU 占用有明显波动，**没有证据证明这次输入优化降低了视频反馈延迟**。首个反馈约 1.1 秒的长尾仍待排查。

`--profile interactive` 仅用于实验：`contentHint=text`、保持分辨率、上限 8 Mbps / 30 FPS，以及可用时把接收端最小缓冲目标设为 0。修正采集页可见性后的这轮实验仍约 30 FPS，码率 7.49 Mbps，点击中位数 64.4 ms，最大值仍 1134.1 ms。它增加带宽且未消除长尾，尚未设为产品默认值。`jitterBufferTarget=0` 不是缓冲时长上限，不能保证零缓冲或固定低延迟。

原始报告位于 `out/remote-perf-active-{baseline,coalesced,interactive}-20261029.json`。这组测量仅覆盖本机页面采集，不能外推到跨设备网络、窗口或桌面采集。下一步优先定位采集／发送队列和接收缓冲的长尾，再对比硬件编解码能力与文字质量。
