# 常用浏览器证书差异清单

核对日期：2026-10-25。本文补充企业 CA 下发协议，列出公开根计划与本地 Chromium 的差异。
本清单是调查记录；后续已实现 [服务端发布与浏览器接入](企业CA客户端部署.md)。
六张候选作为服务端资产按配置下发，没有加入浏览器默认根库或操作系统证书库。

## 1. 比较基线与口径

本地 Chromium 为 `153.0.8004.0`，编译内置 Chrome Root Store（CRS）为 **v37**。
`net/data/ssl/chrome_root_store/root_store.certs` 有 **104 张根证书**，已逐张解析 DER，
核对 SHA-256 与 `root_store.textproto` 的引用一致；其中 26 张根带有额外约束。
另有 17 张中间 CA 标为 `tls_trust_anchor: true`，加上根后共有 121 个编译内置 TLS 信任锚。
`additional_certs` 的其他 141 张属于 EUTL，不能把全部附加证书都当成普通 HTTPS 根。

以下差集仅以这 **104 张根的完整 DER SHA-256** 为基线，不包含机器上的系统证书、用户导入、
企业策略或运行时 PKI Metadata 组件。名称相同、公钥相同和 DER 相同是不同判断。
浏览器版本、操作系统、用途、约束和本地配置均影响最终信任，差集不是默认安装清单。

完整指纹、名称、来源、抓取内容摘要及差集见同目录
`浏览器证书差异清单_2026-10-25.json`，其用途标记为 `research_only_not_trust_configuration`。
文件没有证书 PEM，不是《企业 CA 下发协议设计》第 4 节定义的可下发快照。

## 2. 常用浏览器的来源与差异

| 浏览器/来源 | 本次核对对象 | 条目数 | 本地根指纹未命中 | 解释 |
| --- | --- | ---: | ---: | --- |
| Chrome / Chromium | 上游 CRS v43，2026-10-20 的固定提交 | 99 | 0 | 与本地相比移除了 5 张根；还需同步约束、中间 CA 等元数据 |
| Firefox | Mozilla/CCADB 启用 Websites trust bit 的 PEM | 118 | 17 | 已解析 PEM 重算指纹；还需考虑 Mozilla 代码侧约束 |
| Edge 的微软根计划来源 | Microsoft Status=Included，且 EKU 含 Server Authentication | 204 | 109 | 原始报告共 550 条；差集不是当前 Edge 实机信任测试结果 |
| Safari 所在 Apple 平台 | Apple Root Store 2025082000 的 Included Root CA Certificates 整表 | 156 | 76 | 包含代码签名、开发者等用途，未作 TLS 用途筛选，不能视为 Safari 的 HTTPS 缺根数 |
| 360 | 官方 RSA/ECC 根计划 JSON | 81 | 35 | 46 条指纹匹配；公开列表未绑定具体浏览器构建，部分日期存在错误 |
| QQ、搜狗 | 厂商公开资料检索 | — | — | 本次未找到可验证的完整额外根清单，不推断其额外信任集合 |

Chrome 的公共信任来自 CRS，并支持本地信任决定；Edge 在 Windows/macOS 使用随浏览器分发的
微软根列表并读取本地安装的根。Firefox 也支持操作系统中的企业根和策略安装。
因此“某浏览器能访问”还可能来自那台机器的企业/用户配置，不能据此认定浏览器额外内置了某 CA。
依据：[Chrome FAQ](https://chromium.googlesource.com/chromium/src/+/main/net/data/ssl/chrome_root_store/faq.md)、
[Edge 验证流程](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-security-cert-verification)、
[Firefox 企业 CA](https://support.mozilla.org/en-US/kb/setting-certificate-authorities-firefox)。

报告入口：[Mozilla 根清单说明](https://wiki.mozilla.org/CA/IncludedCertificates)、
[Firefox TLS PEM](https://ccadb.my.salesforce-sites.com/mozilla/IncludedRootsPEMTxt?TrustBitsInclude=Websites)、
[微软根计划列表](https://ccadb.my.salesforce-sites.com/microsoft/IncludedCACertificateReportForMSFT)、
[Apple 清单](https://support.apple.com/en-us/126047)、
[360 RSA/ECC 计划](https://caprogram.360.cn/)。
微软比较未额外按到期日过滤；Apple 的用途限制和 360 的清单日期问题均在 JSON 中保留说明。

## 5. 上游 CRS 更新与“补根”不同

固定比较提交为 `8793082f793c2533dccf28e83e33f0e700c52d28`，
[对应 CRS v43 清单](https://chromium.googlesource.com/chromium/src/+/8793082f793c2533dccf28e83e33f0e700c52d28/net/data/ssl/chrome_root_store/root_store.md)。
相对于本地 v37，根 DER 集合没有新增，以下 5 张不再出现在该清单：

- emSign ECC Root CA - G3。
- GTS Root R2、GTS Root R3。
- ePKI Root Certification Authority（Chunghwa Telecom）。
- NetLock Arany (Class Gold) Főtanúsítvány。

这描述根集合差异，不断言这些公钥在所有路径和浏览器中均不可用。
升级应一并处理上游证书、约束、受信任中间 CA 和元数据，不只拷贝 PEM，也不把移除项补回本地信任。

本地已编译启用 PKI Metadata 组件更新，组件 ID 为 `efniojlnjndmcbiieegkicadnoecjjef`，
通过组件内的 `crs.pb` 更新验证服务。此次没有启动浏览器验证在线更新结果，
所以 v37 是编译基线，不等于实际运行进程一定仍在使用 v37。
后续实施应先验证此链路是否可达，再决定是否随版本同步新的完整上游根库。

## 6. 必须保留的限制与误差

本地内置清单中的 HiPKI G1、旧 SSL.com 四根及部分 DigiCert 根已带 SCT 时间限制：
HiPKI G1 截止 2025-07-31，旧 SSL.com 四根截止 2026-06-14，DigiCert Trusted Root G4
截止 2026-06-30，DigiCert Assured ID G2/G3 截止 2026-09-14（均为 UTC 当日 23:59:59）。
这些是验证策略中的 SCT 条件，不是根证书自身的 NotAfter。
`net/cert/cert_verify_proc_builtin.cc` 的 `CheckChromeRootConstraints()` 会对额外本地信任锚
走例外路径，重复注入可能绕开 CRS 约束，因此不能用企业 CA 下发来“修复”这类策略拒绝。

360 指纹差异还需注意：

- 4 张 GTS R1–R4 对应旧版 DER，本地已有带 digitalSignature 的新版。
  [Google 官方证书库](https://pki.goog/repository/)同时列出新旧版本，不能仅凭 DER 不同判缺 CA 公钥。
- Baltimore CyberTrust Root 已在 2025 年 5 月过期，不列为补充候选。
- 360 把 AffirmTrust Premium 的有效期写到 2025-05-13，
  [CA 官方 CPS](https://www.entrust.com/sites/default/files/documentation/licensingandagreements/archived-legal-agreements/affirmtrust/affirmtrust-ssl-cps-3-12.pdf)
  载明到期日为 2040-12-31。JSON 保留网页原值以便复核，不用它直接决定是否授信。

微软报告中的 Disabled 条目、仅代码签名/邮件用途条目已排除在该报告差集之外。
例如 CNNIC ROOT、WoSign 和 StartCom 的相关旧根不能因为仍可从报告或历史包下载就自动补回。

## 7. 国密证书单独处理

[360 SM2 根计划](https://caprogram.360.cn/smplan.html)及其
[JSON](https://caprogram.360.cn/trusted_root_cert_sm.json)列出 25 项，包括
CFCA CS SM2 CA、GDCA GM SM2 ROOT、BJCA Global Root CA4、vTrus SM2 Root CA G1、
UCA Root SM2、TrustAsia SM2 Root CA / Global SM2 Root CA G2 等。
该 JSON 未提供 SHA-256，因此未把它并入普通 RSA/ECC 的指纹差集。

[360 国密版](https://browser.360.net/gmzb.html?src=browser.360.net)和
[TrustAsia 国密浏览器](https://www.trustasia.com/product/browser)明确介绍了额外密码模块或协议支持。
普通 CA 注入接口本身不会增加 SM2/SM3 或 TLCP 支持；国密站点报错不能直接归因为少装证书。
若后续纳入国密需求，必须另行确定证书算法、TLS/TLCP、密码模块和测试范围。

## 8. 对下发协议的补充结论

1. 公共根默认沿用 CRS 及其约束；企业配置、系统/用户信任和公共根更新保持各自所有权。
2. 本文所有差异是研究记录，发布端不能自动把各浏览器根列表取并集后下发。
3. 当前生效的公共信任锚或同公钥变体不得重复授予 Xenon 本地信任，以免绕过公共根约束。
   运行时检查覆盖组件更新与受信任中间 CA，CRS 变化后重算托管贡献；本文的 104 根只是调查基线。
4. 后续如确需采用某候选，应记录具体 DER/SPKI 指纹、原始证书来源、浏览器计划版本、
   用途/约束、适用业务域和移除/轮换规则，并先验证目标站点完整证书链。
5. 六张候选已提供服务端发布工具与客户端接入，默认关闭，由部署配置决定集合；没有改 Chromium 根库。
